# JxPan Rust 迁移计划

## 目标与边界

- 保留当前 JxPan 的首页、管理后台、登录页面及浏览器 HTML/CSS/JavaScript；第一阶段不重写为 WASM，不改 UI 设计。
- 先完整迁移天翼云盘和移动云盘的链接识别、分享校验、密码验证、目录浏览、文件定位、认证、凭据续期、解析、播放和下载行为。
- 其余网盘按实际需要逐个迁移；未实现能力明确报错，不伪造成功，不悄悄代理旧服务。
- 保留现有 API 参数、JSON 字段、错误语义和 STRM 播放链接。对不安全或明确有问题的旧行为，先记录差异并取得确认，不以“兼容”为由照搬风险。
- 当前实例是行为基准；上游源码和历史提取副本只用于参考，不能替代当前实例的验收。
- 默认只做本地提交；不自动 push，不修改现有部署、数据库或网盘账号内的文件。

## 开发与提交规则

每个功能按以下顺序推进，未完成对比不得提交该功能：

1. 阅读当前实现，列出正常、异常、边界和副作用路径。
2. 从当前实例获得脱敏基准，记录源码/实例版本、请求、状态码、响应头、JSON/页面及结果语义。
3. 先编写回归测试，再用最少必要代码实现。
4. 运行格式、lint、单元/集成测试和当前 JxPan 差分验证。
5. 记录通过项目、差异、性能数据和剩余限制；差异未解释或关键用例未通过，不得提交。
6. 只提交本功能所需文件，提交信息关联验收记录；更新本计划状态。

基准验证默认只使用无副作用请求。扫码确认、凭据保存、转存、删除、清空记录、短链创建等写操作，需明确测试账号、数据范围和授权；不能因为旧实现包含这些路径就直接执行。

## 实现约束

- 单一职责：HTTP/兼容协议、业务编排、网盘适配、存储、缓存、页面资源分别负责自己的边界。
- 先复用已有函数/模块和成熟库，再考虑增加实现；不为“设计模式”增加空接口、工厂、插件框架或重复封装。
- 天翼/移动适配器作为协议 Adapter；业务流程直接组合。出现第二个真实共性实现时再抽取共享能力，必要时使用 Strategy，不提前制造泛化体系。
- 明确类型和错误边界；JSON 兼容字段只放在接口层。允许网盘特有字段，不用一个巨型类型强行统一所有协议。
- 不在异步线程阻塞，不在锁内 await 网络请求，不重复创建 HTTP 客户端，不无界 spawn/重试/排队。
- 默认不写入凭据到日志、测试样本、Git 或短链；所有日志脱敏。签名算法参数、编码、日期和输出格式必须以测试向量验证。
- 性能以测量为准，不承诺未经验证的“最快/最低占用”。优先降低上游请求数、分配和复制，避免破坏正确性换取快。
- 仅按本阶段需要增加依赖和 Cargo features；提交 Cargo.lock；不提前加入 Redis、ORM、微服务或分布式锁。

## 初始架构决策

采用单个 Rust crate；暂不拆 workspace 多包。

- `src/main.rs`：进程启动和关闭。
- `src/config.rs`：启动配置及校验。
- `src/http/`：路由、旧 API 参数/响应兼容、页面服务。
- `src/providers/cloud189*.rs`、`src/providers/mcloud*.rs`：网盘协议、HTTP 适配、认证和业务编排；共性放 `compat.rs` / `tree.rs`。
- `src/storage.rs`：有界工作线程 SQLite KV，凭据/记录/短链路由逐步接入。
- `src/cache.rs`：有界 TTL 与取消安全的请求合并，缓存已序列化响应。
- `web/`：从已确认的当前源码/响应导入的原页面，不混入示例或重新设计的页面。
- `tests/`：路由/协议回归、脱敏样本和差分验证。

HTTP 框架使用 Axum + Tokio，关闭不需要的默认 features。出站客户端待网盘模块需要时引入 Reqwest/Rustls，复用连接池。SQLite、缓存、加密库同样按需要引入，不一次性创建空模块。

## 兼容与验证矩阵

- 页面：首页、后台未登录/已登录、配置、扫码、目录展开/收起、解析弹窗、下载、复制、短链和错误提示。
- 请求：GET 与原 POST 编码、缺失/空值/重复参数、URL 编码、文件 ID 别名、目录链及 sid；未知 action/网盘不可伪造可用。
- 分享：单文件、根目录、多层/空目录、大目录、分页、中文/特殊字符名称、有/无密码、失效、文件不存在。
- 认证：前端/存储/环境凭据的实际优先级，未登录、过期、刷新失败、账号切换、轮询关闭/超时。
- 下载：JSON 与 type=down 区别、重定向、临时 URL 语义有效性、CDN 跳转、HEAD/Range/206/416、上游限流/错误/断开。
- 安全：未授权后台、秘密脱敏、跨账号缓存隔离、过期短链、凭据不进入测试报告、禁止任意地址 SSRF。
- 写操作：独立显式授权；转存和清理必须定位本次测试产生的资源，不得删除账号已有文件。

动态直链、时间戳、随机值不能按字节机械比较。逐字段指定差分规则；对动态值验证类型、协议和有效性，不能笼统删除全部差异字段。

## 性能策略与度量

先保持正确行为，再分离提交每个经测量有收益的优化：

1. 共享 HTTP 客户端/连接池、显式连接与请求超时、并发上限，避免串行的独立请求。
2. 请求合并（single-flight）：相同账号/分享/密码/目录/文件及凭据版本的同类请求只访问一次上游。
3. 有界 TTL 缓存：分别考虑分享、目录和临时直链的有效期；包含账号/凭据版本，不保存明文密码；认证变化立即失效。
4. 不长期缓存认证/限流错误；直链 TTL 不超过上游有效期且留裕量；陈旧数据策略单独验证，不能把失效 URL 返回为成功。
5. 下载优先原有安全重定向；确需代理则流式传输和背压，不整文件收进内存，不对下载响应做压缩。
6. 页面导入后评估静态预编码/压缩和低分配响应；不能因此丢失动态内容、正确的缓存头或认证边界。
7. SQLite 索引、事务、过期清理在实现存储时设计，避免每请求建表或全表扫描。

在同一目标机、同一有效分享和凭据、明确冷/热缓存条件下记录：空闲/峰值 RSS、CPU、线程数、首次解析和播放 p50/p95/p99、吞吐量、上游请求数及缓存命中率。区分网络等待、处理时间和资源用量；没有数据不标记优化成功。
